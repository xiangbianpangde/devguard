## 二、P1（3 项）

### R2-01 · C6 · 豁免到期「语义放行」：无限期豁免可合法登记

- **证据**：`scripts/check_exemption_log.py:78` `EXPIRY_RE = ^\d{4}-\d{2}-\d{2}$`；`:97-106` `validate_expiry` 仅校验非空+格式匹配，**无「到期 ≥ 今天」与「有效期上限」语义检查**
- **复现**（实跑）：构造含 `2099-12-31` 与 `1900-01-01` 到期的豁免记录 → 均 PASS（0 错误）——任何提交者可登记 2099 年到期=无限期豁免；已过期记录同样不被拒绝
- **实际/期望**：C6「有到期」应含语义（今天 ≤ 到期 ≤ 合理上限如 180 天），超限或过期即 FAIL
- **存量审计**：既有 3 条到期均合理（1/2=当天一次性、3=30 天），存量合规；漏洞在 checker 语义层
- **修复建议**：格式校验后加语义界校验 + 违规 FAIL；收束审计复核超长豁免

### R2-02 · S7 · 渲染零转义：STATUS/_meta 任意值可注入 dashboard.html

- **证据**：`docs/templates/devguard/html-report-template/render.py` `render_convention_rows`（L90-108）与 `render_status_rows`（L112-128）以 f-string 直接拼 `title/l1/l3/status/num/name/bdd/date` 进 `<td>`，**全文 0 处 html.escape**
- **复现**（临时副本实测）：STATUS.md 注入 `<script>alert(1)</script>`、`<img src=x onerror=alert(2)>` → 渲染产物原样直出，无任何转义
- **威胁链**：PR 改 STATUS.md 状态列 → 合入 → CI 渲染 dashboard.html → 打开即执行注入 JS
- **期望**：所有插值经 `html.escape`；补注入 fixture → 产物无原始 `<script>` 的回归测试
- **注**：蓝队工作区已有 render.py 转义改动（在途未提交），入库后红队复验

### R2-04 · C3 · CI 运行时供应链：浮动依赖 + npx latest 绕过 lock

- **证据**：`ci.yml:37/195` `pip install pyyaml` 浮动；`:63` `pip install import-linter` 浮动；`:68` `npx --yes @stoplight/spectral-cli` 取 latest、**完全不在 package-lock**；`npm ci`(:57) 使用 lock v3 且 171 包全有 integrity（正向✅），但 spectral 绕过锁
- **实际**：CI 每次运行依赖上游最新版=不可复现+供应链执行风险
- **期望**：spectral 入 package.json/lock + `npx --no-install`；pyyaml/import-linter 钉版或 `--require-hashes`
- **修复建议**：全部依赖进入 lock 或精确钉版

## 三、P2（4 项）

### R2-03 · D1 · 远程安装无完整性校验 + master raw 未钉版

- **证据**：README:71-84 官方推荐 `curl -fsSL .../master/scripts/install.sh | bash`；install.sh/install.ps1 全文无 sha256/signature 校验（receipt sha256 是写后完整性，非下载源验证）；v2.5.0 Release 无任何 assets（GitHub API 确认）
- **威胁模型**：raw.githubusercontent 投毒（仓库接管/CDN 污染/上游失陷）→ 用户执行恶意代码；且指向 **master** 而非 release tag——每次 push 都改变安装内容
- **期望**：README 提供固定版本 SHA 清单或签名校验；主路径改 `git clone` + 本地执行，curl|bash 降级为「已核验 SHA 的高级用法」
- **缓解现状（肯定）**：fail-closed 设计（无法自我定位时提示 clone，不静默降级）

### R2-05 · C3 · CI 权限未最小化 + action tag 钉版（在途修复中）

- **证据**：HEAD 3cb59ef 的 ci.yml 无 workflow 级 `permissions`；actions/checkout@v4、setup-python@v5 以 movable tag 钉版（5 job 各重复）
- **在途状态**：蓝队工作区已加 `permissions: contents: read` + SHA 钉版；**但首版 SHA 无效**（API 422，红队拦截预警），蓝队已按红队提供值修正为真实 SHA（checkout@`11d5960a3267...`、setup-python@`a26af69be951...`）——未提交，入库后红队复验
- **过程记录**：在途无效 SHA 若入库将致 CI 全失败，属防御提交质量事故，红队预警后即时改正
- **修复建议**：另评估 `persist-credentials: false`（checkout 默认持久化 token 到本地 git 配置）

### R2-06 · C2 相邻 · pre-commit 第三方钩子供应链：movable tag 钉版

- **证据**：`.pre-commit-config.yaml:12-35` 3 个远程 repo 均 tag 钉版（pre-commit-hooks v5.0.0 / ruff-pre-commit v0.15.20 / gitleaks v8.24.3），无 commit SHA；scaffold 同款
- **威胁模型**：上游 tag 被移动 → 开发者机器与初始化项目执行恶意 hook（代码执行级）
- **期望**：真源渲染改 40 位 SHA + 注释版本号；加 immutable-rev checker；或接受风险并文档化（需 Owner 决策）

### R2-07 · 平台层文档声称 vs API 事实漂移

- **证据**（公开 API，无 token）：master 分支 protected=true，required contexts 恰为 5 个：L1 lint / pytest / L4 convention / Compliance / Build；跨平台 job 的 check runs 存在但**未直接列入 required contexts**（经 Build needs 间接阻断）——SECURITY.md:25/28 声称 required checks 含跨平台，与 API 事实不完全一致
- **不可验证项**：`/branches/master/protection` 细节（401）、push protection endpoint（404）、Dependabot（401）——无 token 均无法确认；**SECURITY.md 不应声称已启用未经确认的防护**
- **期望**：Owner 携 admin token 核对后按事实修正 SECURITY.md 表述；或明确标注「待确认」
