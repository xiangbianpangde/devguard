§ 01 · ANTI-PATTERNS

旧 LLM 应用：5 个典型崩塌

未把"提示词 / 上下文 / Loop / Harness"分而治之的项目，几乎必然踩中以下 5 个崩塌。每条都是真实案例浓缩。

① 提示词崩塌 · 单体巨型 prompt

把"角色 + 任务 + 格式 + 约束 + 例子"全塞一段 8K token 的 system prompt。问题是：模型对 prompt 中段指令遵循率显著低于首尾（"lost-in-the-middle"），且无法局部调优。

lost-in-the-middle不可调试无法 A/B

② 上下文崩塌 · 把历史当真理

把"之前的工具输出"原封不动塞回下一轮 context。结果：tool 错误被无脑复制、文件路径飘移、长上下文性能悬崖。

context 污染路径飘移性能悬崖

③ Loop 崩塌 · 无收敛的反复问

Agent 一直 repeat "let me try again" 直到 token 耗尽。本质是没有"何时该停"的控制循环。

死循环无终止条件无 retry-budget

④ Harness 崩塌 · 工具定义放任

工具 schema 写得模糊、参数无约束、错误信息不可执行。结果：模型猜参数名、栈 trace 一坨、token 浪费在 debug。

tool taxschema 模糊错误不可执行

⑤ 反馈崩塌 · 修了再修同一个坑

失败案例不归档、修复结果不复测。下次同问题再翻车。这是 Loop + 记忆 双缺失。

无反思无回归无 lessons learned

共性根因 · 缺一顶"工程帽子"

四支柱任一缺失，都会从对应方向崩塌。提示词写得再好，没有 Loop 也会死循环；Loop 设计再精，没有 Harness 也无工具可用。

提示词上下文LoopHarness

§ 03 · 12-DIMENSION MATRIX

12 维技术矩阵 · 4 支柱 × 3 维度

把每个支柱的工程实践拆成"输入 / 处理 / 输出"三维度。共 12 格，每格有明确的可验收产物。

支柱输入维度处理维度输出维度落地配置
提示词 用户请求 + 系统约束 结构化模板（角色/任务/格式/约束/示例） 单一可复用的 system prompt YAML Jinja
上下文 历史消息 + 工具结果 + 文件内容 分层预算（系统/工具/历史/对话） 截断后的有效 context context budget RAG
Loop 当前观察 + 历史决策 决策 + 派发 下一动作或终止信号 max-steps retry-budget
Harness 工具调用意图 schema 校验 + 权限闸门 真实工具副作用 JSON Schema sandbox

5 条红线 · 任一踩中视为"工程不合格"

红线 1 · 提示词硬编码 token

不可参数化的字符串模板不算提示词工程。

红线 2 · 上下文无截断

任由 context 增长到 100K+ 才处理，性能悬崖必现。

红线 3 · Loop 无终止

没有 max_steps / max_tokens / 任务完成判定，必然死循环。

红线 4 · 工具无 schema

tool 定义只有"名字+描述"，参数自由发挥，幻觉率爆炸。

红线 5 · 无回归测试

改完提示词不复测，下次同问题再翻车。

达标门槛 · 4/5 红线全清 + L4 套件 100% pass

本框架下"AI 工程合格"的硬闸门。

§ 06 · CONTROL LOOP

Loop 控制循环 · 四阶段 + 收敛闸门

Loop 是 Agent 的"心脏"。四阶段：观察 → 决策 → 派发 → 评估。缺一即停摆。

[观察 OBSERVE] 收集本轮所有可观察信息 ↓ [决策 DECIDE] 模型基于观察决定下一步 ↓ [派发 DISPATCH] 工具调用 / 子 agent / 终止 ↓ [评估 EVALUATE] 任务是否完成？资源是否耗尽？ ↓ ↺ 未完成 → 回到观察 → 完成 → 终态报告

旧范式：if/else + try/except

硬编码分支，5 个 case 后失守。

if err:
    retry()
elif timeout:
    backoff()
else:
    continue()
→

四支柱范式：控制循环 + 闸门

声明式终止条件，资源上限兜底。

while not converged(state):
    obs = observe()
    act = decide(obs, history)
    result = dispatch(act)
    state = evaluate(state, result)
    assert state.steps < MAX_STEPS
